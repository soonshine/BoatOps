D1 does not authorize production inventory activation, real data, Google Sheet migration, ChannelHub, OTA, WordPress, payments, Tag, GitHub Release, or G2 work.

## Runtime mode

D1 introduces `isolated_operator_demo` rather than weakening `public_read_only`.

The mode requires all of the following before any application route is served:

- `APP_ENV=production`
- `BOATOPS_DEMO_SITE_ENABLED=true`
- `BOATOPS_DEMO_SITE_MODE=isolated_operator_demo`
- `BOATOPS_DEMO_SITE_ISOLATED_DATASET=true`
- effective database driver is SQLite, including all configured overrides
- `CACHE_STORE=file`
- rate limiter uses the file cache
- `SESSION_DRIVER=file`
- `QUEUE_CONNECTION=sync`

The isolation flag remains an assertion that the database contains only the dedicated fictional Demo organization and must never be used for a shared or real BoatOps database.

## HTTP boundary

In `isolated_operator_demo`:

- `/api` and `/api/*` remain closed with 404 before normal API execution.
- `/demo`, `/demo/calendar`, and `/demo/slots` remain GET-only through `ResolveDemoSiteContext`.
- non-GET requests outside `/operator/*` are rejected with 405 before routing/controller execution.
- G1 `/operator/*` GET and POST routes may execute against the isolated fictional SQLite database.
- file-backed sessions are permitted for synthetic Operator authentication.
- no database-backed cache, session, rate limiter, or queue is permitted.

The existing `public_read_only` behavior is unchanged: Operator GET remains 404 and every non-GET application request remains 405.

## Fictional Operator bootstrap

`Database\Seeders\OperatorDemoSeeder` is a dedicated D1-only bootstrap. It may run only when the effective runtime is production `isolated_operator_demo` with isolated SQLite.

The bootstrap requires:

- `BOATOPS_DEMO_OPERATOR_EMAIL` ending in the reserved `@example.test` domain;
- `BOATOPS_DEMO_OPERATOR_PASSWORD` of at least 24 characters;
- exactly one organization matching `Fictional Andaman Charter Lab`.

It creates or updates only the named synthetic Operator and its membership in that one fictional organization. It grants the three G1 MVP permissions: calendar read, booking workflow, and BLOCK workflow. A pre-existing user with the configured email but a non-Demo name, or a membership attached to another organization, fails closed.

The synthetic password must be supplied through the server secret/environment path and must not be committed, printed, included in a command argument, browser artifact, report, or deployment receipt.

## Deployment sequence

The server-side D1 switch must preserve the D0.1 atomic release/rollback pattern:

1. Verify the candidate source identity and successful exact-head CI.
2. Capture the current release ID and retain the current D0.1 release.
3. Back up the isolated SQLite artifact set and verify integrity, foreign keys, canonical state, and row counts before modification.
4. Build a new immutable release directory from the reviewed D1 head.
5. Reuse the existing isolated fictional SQLite database only after its backup is verified.
6. Run only pending BoatOps migrations against that isolated fictional database.
7. Set `BOATOPS_DEMO_SITE_MODE=isolated_operator_demo` and the approved file/sync runtime drivers.
8. Supply synthetic Operator credentials through the server secret/environment path and run only `php artisan db:seed --class="Database\\Seeders\\OperatorDemoSeeder" --force`.
9. Remove the bootstrap password from any transient shell environment immediately after the command. Do not write it into release metadata.
10. Clear/rebuild Laravel caches under the production web user and verify writable file cache/session paths.
11. Atomically switch the `current` symlink, reload PHP-FPM, and require `nginx -t` success.
12. Execute external acceptance and, on any failure, atomically restore the retained D0.1 release.

No `DemoSiteSeeder`, real-data migration, PostgreSQL migration, queue worker enablement, scheduler enablement, Tag, Release, or production-master switch is part of D1.

## Required live acceptance

D1 is not complete until all of the following are recorded from the deployed candidate:

- `/up`, `/`, `/demo`, `/demo/calendar`, `/demo/slots`, and `/operator/login` return the expected successful responses.
- `/api/*` representative requests return 404 with and without a fictional credential.
- non-GET `/demo/*` representative requests return 405.
- unauthenticated protected `/operator/*` pages redirect to `/operator/login` rather than exposing data.
- synthetic Operator login succeeds and lands on the first permitted G1 page.
- calendar, inquiry creation, HOLD, confirm, amend/cancel, BLOCK/release, and audit surfaces execute only inside the fictional organization.
- an unrelated synthetic organization, if included in acceptance fixtures, receives no writes.
- file cache/session are writable by the production web user and SQLite remains the only application database.
- queue remains `sync`; no BoatOps scheduler or asynchronous worker is enabled by D1.
- no real customer, price, contract, operations, Google Sheet, ChannelHub, OTA, WordPress, payment, or production credential is present.
- an actual rollback to retained D0.1 and restoration to D1 succeeds before final acceptance.

Because G1 Operator workflows are intentionally interactive, the D1 SQLite application state is expected to change during authenticated acceptance. D1 therefore requires a verified pre-deployment backup and organization-scoped write evidence rather than the D0.1 public-GET immutability criterion.

## Stop conditions

Stop and restore D0.1 immediately if any of these occur:

- the effective database is not the approved isolated SQLite file;
- the database contains a real or unexpected organization;
- API routes become reachable;
- a public `/demo` write reaches a controller;
- credentials appear in logs or command output;
- cache/session/queue resolve to database-backed state;
- migration or Operator bootstrap touches an unexpected organization;
- live G1 workflow acceptance fails;
- rollback evidence cannot be reproduced.

D1 completion does not authorize G2A. G2A starts only after D1 deployment evidence is independently reviewed and the next bounded gate is recorded.
